# Phase 3 Architecture — Mobile Shell (Expo)

**Status:** implemented and verified via `expo start --web` — a real browser session (Chrome, via the `expo-web` bundler target) ran the actual app end-to-end: entered an API key, sent a chat message, watched the `AgentLoop` state machine transition `OBSERVE -> PLAN`, and watched `GeminiProvider` make a real network call to Gemini's REST API (which failed with a real `400` for the deliberately-invalid test key — the failure itself, and its now-visible rendering in the chat transcript, is what this session verified; see §5). **No iOS/Android simulator or `adb` was available in this environment**, so biometric approval, on-device storage (`expo-secure-store`/Keychain), and the real native build have not been run on a device — see §6's scope note. See [`docs/PRD.md`](../PRD.md) §1.3/§1.4/§5.1/§6.4/§7.2 for the spec; [`phase-3-desktop.md`](./phase-3-desktop.md) is this phase's other half (`apps/desktop`), covered separately since the two apps share no code and solve structurally different problems — desktop is a thin gRPC client, mobile runs `agent-core` in-process.

## 1. Why this is architecturally different from every prior app

Every previous client (`apps/cli`, `apps/desktop`) is a thin transport to `talond`, which hosts `agent-core`. PRD §1.3/§1.4 require something different for mobile: React Native's Hermes engine cannot host a Node daemon, so `@talon/agent-core`'s loop runs **in-process inside the app itself**. This is the first time `agent-core` has ever run outside `talond` — and the first time anything in this codebase has had to confirm `agent-core` is actually portable to a non-Node runtime, not just type-compatible with one.

It wasn't, quite: `agent-loop.ts` imported `randomUUID` from `node:crypto` — harmless everywhere `agent-core` had run before (always inside `talond`, a real Node process), fatal under Hermes, which has no Node core modules at all. **Fixed in `packages/agent-core/src/loop/agent-loop.ts`**: swapped for `globalThis.crypto.randomUUID()`, a standard Web Crypto API present in Node 19+, Hermes/React Native, and browsers alike — bringing `agent-core` in line with the PRD §1.1 promise ("pure, dependency-free TypeScript with no Node-specific... APIs") it had quietly been violating since Phase 1. This is the one change in this phase that touches a shared package rather than `apps/mobile` itself, and every existing test/build/lint pass confirms it's a no-op everywhere else.

A second, smaller gap: `packages/agent-core/src/index.ts`'s barrel exported `ModelProviderPort`/`ToolRegistryPort`/`ApprovalGatePort` — the three ports PRD §2.2 calls "the only extension points" — but never `MemoryPort`/`SkillsPort`, despite both existing in `shared/ports.ts` for exactly this purpose (phase-2.md §2.1/§4.2's own framing: "the PRD gives `agent-memory`/`agent-skills` no formal interface... this port fills that gap"). Nothing needed to import them externally before, since `@talon/agent-memory`/`@talon/agent-skills` only ever satisfy them structurally, without a literal `implements`. Mobile's own memory/skills stubs (§4) are the first *external* implementers, so this phase adds all five (`MemoryPort`, `MemoryTurn`, `SkillsPort`, `SkillCatalogEntryPort`, `SkillActivationPort`, `SkillActivationContextPort`, `SkillDraftEvaluationPort`) to the barrel — closing a real gap, not a new concept.

## 2. What can't be reused from the Node-side packages, and why

`@talon/agent-tools`, `@talon/agent-memory`, and `@talon/agent-skills` all exist already — but none of them run under Hermes:

- `agent-tools`' `ToolRegistry` unconditionally constructs a `ToolSandbox` in its own constructor, which imports `node:net` and `execa` (a process-spawning library) — importing anything from this package's barrel at all would try to bundle a Node-process-spawner into the Metro build.
- `agent-memory`'s `MemoryStore` is built on `better-sqlite3`, a native Node addon — there is no Hermes build of it, and couldn't be (it's compiled C++, not JS).
- `agent-skills`' `SkillCatalog` reads `.md` files via `node:fs`/`node:url` (`import.meta.url`-based path resolution) — no filesystem API shaped like that exists on mobile either.

So `apps/mobile/src/agent/` writes its own, from scratch, each one structurally satisfying the same port `agent-core` already defines — exactly the same relationship `agent-tools`' `ToolRegistry` has to `ToolRegistryPort`, just a second, independent implementer:

| Port | Desktop/talond implementer | Mobile implementer |
|---|---|---|
| `ModelProviderPort` | `OllamaProvider` (`agent-providers`) | `GeminiProvider` (`agent-providers` — shared, see §3) |
| `ToolRegistryPort` | `ToolRegistry` (`agent-tools`) | `MobileToolRegistry` (`mobile-tools.ts`, new) |
| `ApprovalGatePort` | `ApprovalGate` (`agent-tools`) | `MobileApprovalGate` (`mobile-approval-gate.ts`, new) |
| `MemoryPort` | `MemoryStore.createSession()` (`agent-memory`) | `NoopMobileMemory` (`mobile-memory.ts`, new — §6) |
| `SkillsPort` | `SkillCatalog` (`agent-skills`) | `NoopMobileSkills` (`mobile-skills.ts`, new — §6) |
| `Channel` | `GrpcChannel` (`apps/talond`) | `MobileChannel` (`mobile-channel.ts`, new) |

## 3. `GeminiProvider` — the one new addition to a shared package

Lives in `packages/agent-providers/src/gemini/gemini-provider.ts`, per PRD §6.4, re-exported from the package barrel alongside `OllamaProvider`. It's a shared package (not `apps/mobile`-only) because PRD §3.3's eventual router needs it available to `talond` too, even though Phase 3 only wires it into mobile.

**One deliberate divergence from the PRD's own snippet:** §6.4 sketches `streamGenerateContent?alt=sse` with incremental SSE parsing. This provider calls the **non-streaming** `generateContent` endpoint instead. Every other provider in this package only ever runs inside `talond` (a real Node process) and can safely assume Node's `Readable.fromWeb` stream-reading APIs (see `OllamaProvider`) — `GeminiProvider` is the first one PRD §7.2 requires to *also* run in-process on mobile, where streaming-body `fetch()` support is version-dependent and, in this environment, literally untestable (no device/simulator — see §6). Rather than branch the one implementation by runtime, it stays one code path that's correct everywhere: still exposes the same `AsyncIterable<CompletionChunk>` contract every provider does, it just yields its chunks after one round-trip instead of as they stream in. Revisit once a concrete RN streaming-fetch capability is confirmed on a real device.

Two smaller, load-bearing fixes inside it, both covered by `test/gemini-provider.test.ts`:

- **No `process.env`.** The PRD's snippet reads `process.env.GEMINI_API_KEY`; this provider takes the key as a constructor argument instead — `process.env` isn't meaningfully available at runtime on Hermes the way it is in Node (Expo only inlines `EXPO_PUBLIC_`-prefixed vars at *build* time, not a live environment), and PRD §1.1's "user-supplied API key" implies something entered at runtime anyway (apps/mobile's own API-key prompt, §5).
- **Gemini's `contents` array only accepts `"user"`/`"model"` roles** — `agent-core`'s `Message.role` includes `"system"` and `"tool"`, neither of which Gemini's API will accept there. System-role turns are collected into a separate top-level `systemInstruction` field; tool-role turns become a `"user"`-role `functionResponse` part. That part needs the *function's name*, which `Message` doesn't carry (only `toolCallId`, the call's id) — the provider keeps a private `Map<callId, functionName>`, populated whenever it parses a `functionCall` out of a prior response, consulted when building the next request's `functionResponse`. A known, documented limitation: this map is unbounded for the provider instance's lifetime (acceptable — call ids are unique, and a mobile app's provider instance doesn't live as long as `talond`'s daemon-lifetime one does) and falls back to the raw call id if an entry is missing (e.g. a provider recreated between a tool call and its result — not a path this codebase actually takes today).

## 4. `apps/mobile`'s own agent wiring (`src/agent/`)

`agent-session.ts`'s `AgentSession` is the mobile mirror of `apps/talond/src/grpc-server.ts`'s `createTalonDaemonServer()` — the one place this app constructs an `AgentLoop` and plugs in all six ports from the table above. Each mobile-only port:

- **`MobileChannel`** (`mobile-channel.ts`) — an `AsyncQueue`-backed `Channel`, structurally identical to `apps/talond/src/async-queue.ts`'s `AsyncQueue` + `GrpcChannel` pairing, reimplemented rather than shared (the second place this exact small pattern lives, not the third — phase-1.md §8's own threshold). Never closes; a mobile session runs for the app's lifetime, the same way `GrpcChannel` runs for one gRPC stream's.
- **`MobileToolRegistry`** (`mobile-tools.ts`) — `device.info` (`safeReadOnly`, `react-native`'s `Platform`), `fs.read_file`/`fs.list_dir` (`safeReadOnly`, matching the PRD §5.1 matrix row exactly) scoped to the app's sandboxed document directory via `expo-file-system`'s **current** API (`Paths`, `File`, `Directory` classes — the `documentDirectory` constant and `readAsStringAsync`/`readDirectoryAsync` free functions this was first written against were removed from `expo-file-system` well before SDK 58; caught by the typecheck failing against the real installed package, not assumed from stale docs). Containment is a plain string check (reject `..` or a leading `/`) rather than `path.resolve` + prefix comparison (the desktop/talond builtin's approach, `packages/agent-tools/src/builtin/fs-read-file.ts`) — `node:path` doesn't exist under Hermes either.
- **`MobileApprovalGate`** (`mobile-approval-gate.ts`) — PRD §5.1's mobile row literally: `dangerousConfirmRequired` is mandatory biometric via `expo-local-authentication`, never cached; every other tier that reaches this gate at all (`agent-core`'s own `preApproval()` already short-circuits `safeReadOnly` before `ApprovalGatePort.request()` is ever called — so in practice only `heuristicSandboxed` reaches here) gets a lightweight, non-biometric in-flow banner instead (`InlineApprovalBridge`, implemented by `App.tsx`'s `ChatScreen`). If there's no biometric hardware/enrollment (true of `expo start --web`, and of a simulator with no enrolled biometrics), it falls back to the same inline banner — strictly weaker than §5.1's mandate, so this fallback must never be the path a real device with Face ID/Touch ID/BiometricPrompt enrolled takes.
- **`NoopMobileMemory`/`NoopMobileSkills`** (`mobile-memory.ts`/`mobile-skills.ts`) — see §6.

## 5. A real bug found only by sending an actual message

`AgentSession.start()` fires `loop.run()` without awaiting it, matching the "fire-and-forget, errors can't propagate to a caller that's gone" pattern this package already uses elsewhere (phase-2.md §5's synthesizer). Catching the rejection and routing it only to `console.error` seemed like a reasonable match for that pattern — until actually sending a message through the live `expo start --web` session against a deliberately invalid API key: `GeminiProvider` threw a real `400`, and **nothing in the UI changed at all**. No error, no stuck-forever indicator, nothing — the composer stayed enabled, as if the app were still working.

The reason: unlike `talond`, which constructs a *new* `AgentLoop` per gRPC session (so one session's fatal error doesn't affect the next connection), mobile has exactly **one** `AgentLoop` for the app's entire lifetime. Once `run()` throws, that loop is done — every future `sendMessage()` call pushes into a `MobileChannel` whose consumer has already exited, forever, silently.

**Fix**, in `agent-session.ts`: `AgentSessionCallbacks` gained a required `onError(error)` callback, called once if `run()` ever rejects; `AgentSession` also tracks an `ended` flag, and `sendMessage()` checks it — calling `onError` again with an explicit "session has ended, restart the app" message instead of silently queuing into a dead channel. `App.tsx`'s `ChatScreen` renders whatever `onError` reports as a visible red line in the transcript. This was verified live: a second message sent after the first `400` now produces "the agent session has ended after a previous error — restart the app to continue" in the transcript, instead of nothing.

This is a deliberately minimal fix — not a session-restart mechanism. Automatically reconstructing a fresh `AgentLoop` after a fatal error is plausible future work, but wasn't the gap actually found here: the gap was *silence*, not *lack of recovery*.

## 6. Known Phase 3 (mobile) simplifications

- **No persistence.** `NoopMobileMemory`/`NoopMobileSkills` are empty, in-memory stubs — mirrors Phase 1's own "no persistence yet" scope cut for `talond` (phase-1.md §7), not a mobile-specific shortcut. A real implementation needs `expo-sqlite`, gated on PRD §7.3's still-open "confirm FTS5 ships in `expo-sqlite`... resolve before Phase 3" risk — tracked, not resolved by this work.
- **Not verified on a real device or simulator.** This environment has no Xcode simulator tooling and no `adb`; `expo start --web` is the only verification path available, and it was used for everything in §1/§5. Biometric approval, `expo-secure-store` (Keychain/Keystore), and `expo-file-system`'s native (non-web) backend are implemented and typecheck against the real installed packages' API, but have only been exercised by code review, not a live run — `expo-local-authentication`'s `hasHardwareAsync()`/`isEnrolledAsync()` both report false under `expo start --web`, so the biometric branch in `mobile-approval-gate.ts` has never actually executed in this environment, only its non-biometric fallback branch has.
- **One provider, no router.** `GeminiProvider` with a single Flash-class model id — PRD §3.3's full Local → Small Cloud → Premium Cloud escalation ladder is Phase 4 scope.
- **No Apple FM / LiteRT bridges.** PRD §7.2 explicitly defers on-device NPU inference (`modules/apple-fm-bridge`, `modules/litert-bridge`) to Phase 4 — this phase's `apps/mobile` has no `modules/` directory at all yet.
- **API key stored in `localStorage` under `expo start --web`.** `src/settings/api-key-store.ts` uses `expo-secure-store` for the real iOS/Android path; the web fallback is explicitly dev-only and insecure, used only because this is the one target actually reachable in this environment.
- **Minor web-only layout quirk.** `SafeAreaView` doesn't stretch to full viewport height under `react-native-web` without extra root-level CSS some Expo web templates include; harmless and specific to the verification harness, not the shipped native target, so left as-is rather than chasing a fix for a platform this app was never meant to ship on.

## 7. Extending this shell

- **New mobile-safe tool:** add it to `mobile-tools.ts`'s `MobileToolRegistry` default set — no `agent-core` change needed, it only ever sees `ToolRegistryPort`.
- **Real persistence:** replace `NoopMobileMemory`/`NoopMobileSkills` with `expo-sqlite`-backed implementations once PRD §7.3's FTS5 risk is resolved; `agent-session.ts`'s wiring is the only call site that needs to change.
- **Local NPU (Phase 4):** add `modules/apple-fm-bridge`/`modules/litert-bridge` per PRD §6.1/§6.2, and a corresponding `ModelProvider` in `agent-providers` — `agent-session.ts` swaps which provider it constructs, nothing else in this app changes.
